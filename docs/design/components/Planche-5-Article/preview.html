Faire tourner un modèle de langage sur une machine modeste

Ce qu'on gagne et ce qu'on perd en gardant le modèle chez soi, quand les services payants sont exclus.

2026-09-02—12 min de lecture
  • IA appliquée
  • Docker
  • OCR

Sur UGB Link, les services payants étaient exclus. Pour extraire les pièces des dossiers de candidature, il fallait un modèle de langage qui tienne sur la même machine virtuelle que l'application.

Ce billet résume la démarche : choisir la taille du modèle, isoler son conteneur, et accepter le temps de réponse qui va avec.

01Choisir la taille avant le modèle

La première contrainte n'est pas la qualité, c'est la mémoire. Un petit modèle qui laisse de la place à l'API, à PostgreSQL et à Redis vaut mieux qu'un modèle plus capable qui fait tomber le reste.

La limite mémoire du conteneur est une vraie décision d'architecture : elle protège les autres services quand le modèle travaille.

02L'OCR d'abord, le modèle ensuite

Le modèle ne lit pas les images. L'OCR produit le texte, le modèle le structure en champs, et un agent valide.

03Vivre avec le temps de réponse

Une extraction n'a pas besoin d'être instantanée. Elle part en file d'attente, et l'agent est prévenu par une notification text/event-stream quand le résultat est prêt.

À retenir
  1. Choisir la taille du modèle d'après la mémoire disponible, puis mesurer.
  2. Rendre l'extraction asynchrone : l'utilisateur n'attend pas le modèle.
  3. Garder un humain pour valider : le modèle propose, il ne décide pas.
