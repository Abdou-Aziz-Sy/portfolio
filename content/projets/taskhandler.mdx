## Contexte

<Prose>
Cours de génie logiciel de master 1, second semestre : mener un projet à quatre, de bout en bout, avec les méthodes et les outils du métier — branches par fonctionnalité, revues croisées, intégration continue.

L'application gère des tâches d'équipe : création, affectation, suivi jusqu'à la clôture. Je suis le deuxième contributeur du dépôt avec 20 commits, et mon périmètre était le **domaine des tâches** et le socle de données.
</Prose>

<Prose>
Un Spring Boot découpé par responsabilité : contrôleurs, services, dépôts Spring Data, objets de transfert, et une couche d'exceptions dédiée. PostgreSQL pour les données, avec des migrations SQL versionnées. React côté interface.

<DecisionRecord

  titre="Une seule forme d'erreur pour toute l'API"
  contexte="Chaque contrôleur renvoyait ses erreurs de validation à sa façon. L'interface devait deviner la forme de la réponse selon la route appelée."

  decision="Un gestionnaire global intercepte les erreurs de validation et les exceptions métier, et les rend dans une forme unique, champ par champ."

Deux réponses de l'API, dans la forme que leur donne le gestionnaire global : une erreur de validation, champ par champ, puis une transition refusée.

```json
{
  "status": 400,
  "message": "Erreur de validation",
  "timestamp": "2025-06-01T10:15:30",
  "errors": {
    "title": "Le titre est obligatoire",
    "priority": "La priorité est obligatoire"
  }
}
```

```json
{
  "status": 400,
  "message": "Transition invalide: impossible de passer du statut 'Annulé' au statut 'En cours'",
  "timestamp": "2025-06-01T10:16:02"
}
```

## Ce que je referais autrement

<Prose>
J'écrirais les transitions permises comme une table de vérité, dans un seul endroit, plutôt que dispersées dans les conditions du service. La règle serait lisible d'un coup d'œil, et les tests pourraient la parcourir exhaustivement au lieu de vérifier les cas auxquels on a pensé.
</Prose>
