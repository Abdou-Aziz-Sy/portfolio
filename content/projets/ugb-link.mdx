## Décisions

<DecisionRecord
  numero="01"
  titre="Un modèle de langage auto-hébergé plutôt qu'une API"
  contexte="Créer un appel à candidature obligeait à ressaisir à la main le document officiel : titre, dates, frais, pièces requises. Les services tiers payants sont exclus du projet, et la machine virtuelle n'a pas de GPU."
  options={[
    { libelle: "API de modèle hébergée", note: "exclue : payante, et les documents sortiraient du serveur" },
    { libelle: "Règles d'extraction sur le texte", note: "fragiles d'un document à l'autre" },
    { libelle: "Petit modèle de langage auto-hébergé", retenue: true },
  ]}
  decision="L'agent importe le document de l'appel. Le texte est lu directement, ou par OCR s'il est scanné, puis confié à un petit modèle qui tourne dans son propre conteneur et répond dans un format JSON imposé. Le formulaire se pré-remplit et l'agent le valide."
  consequences="Aucun coût par requête, aucune donnée qui sort du serveur. Sans GPU, l'inférence prend plus d'une minute : l'extraction est donc asynchrone et son résultat est poussé à l'agent quand il est prêt."
/>

<DecisionRecord
  numero="02"
  titre="Server-Sent Events plutôt que WebSocket"
  contexte="Les agents doivent voir arriver les changements — bordereaux, courriers, candidatures, paiements, notifications, résultats d'extraction — sans recharger la page. Le flux ne va que du serveur vers le navigateur."
  options={[
    { libelle: "WebSocket", note: "bidirectionnel, inutile ici" },
    { libelle: "Interrogation périodique", note: "charge et latence inutiles" },
    { libelle: "Server-Sent Events", retenue: true },
  ]}
  decision="Chaque onglet ouvre un flux text/event-stream servi par l'API Express. Un bus d'événements en mémoire distribue chaque message aux seuls utilisateurs ou rôles concernés ; sans audience précisée, personne ne le reçoit."
  consequences="Un simple flux HTTP, plus léger à exploiter qu'un serveur WebSocket. Derrière Nginx, il faut désactiver la mise en mémoire tampon de la réponse et envoyer un ping toutes les 25 secondes pour éviter les coupures. À revoir si un besoin bidirectionnel apparaît."
/>

<DecisionRecord
  numero="03"
  titre="Des tests bout en bout plutôt que des tests unitaires"
  contexte="Il fallait vérifier les parcours réels — routes, rôles, base de données — et empêcher le retour des incidents de production."
  options={[
    { libelle: "Tests unitaires d'abord", note: "loin des incidents réels" },
    { libelle: "Tests bout en bout de l'API", retenue: true },
  ]}
  decision="Treize domaines de l'API sont couverts de bout en bout, contrôles d'accès inclus."
  consequences="Les incidents de production ont donné lieu à des cas de non-régression. Contrepartie : des suites plus lentes, et des tests unitaires à poser plus tôt."
/>
